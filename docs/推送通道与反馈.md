# 推送通道与反馈

> 三个出口怎么配、消息长什么样、反馈怎么记账。实现见 [`intel/push.py`](../intel/push.py)、
> [`intel/render.py`](../intel/render.py)、[`intel/feedback.py`](../intel/feedback.py)。

## 1 三个通道

| 通道 | 形态 | 能力 | 适合 |
|---|---|---|---|
| 飞书 | 自定义机器人 webhook | 卡片，能放 6-8 条，支持 markdown 富文本 | 主阅读面 |
| 飞书 | 企业自建应用（`mode=app`） | 主动发消息、列群、写待办 | 团队 / 多目标 |
| 钉钉 | 群机器人 webhook + 加签 | markdown（整批一条） | 已有钉钉群 |
| Telegram | Bot API | 一条事件一条消息，4096 字符上限 | 移动端速读 |

分流不是「同一份内容发三个地方」，而是不同置信度走不同节奏：

- **immediate**（置信 ≥ 0.80）——单条，立刻发；
- **daily**（0.35–0.80）——合并成日报；
- **静默**（最高置信 < `filter.silence.min_confidence`）——只入库，留到晚间简报。

幂等键是 `canonical_url + channel`，30 天内不重发。这一层必须存在：即使水位线失效、
脚本被手动重跑两次，用户也不会收到重复推送。

## 2 飞书

**自定义机器人（最快）**

```bash
export FEISHU_WEBHOOK='https://open.feishu.cn/open-apis/bot/v2/hook/xxx'
export FEISHU_SECRET='...'      # 开启签名校验时必填
python main.py config set --channels feishu
python main.py feishu test
```

**企业自建应用（可列群、可主动发）**

```bash
export FEISHU_APP_ID='cli_xxx'
export FEISHU_APP_SECRET='...'
python main.py config set --channels feishu --feishu-mode app
python main.py feishu chats                 # 列出机器人所在群
python main.py config set --feishu-receive-id oc_xxx
python main.py feishu test
```

签名：以 `{timestamp}\n{secret}` 为 key、空串为 body 做 HmacSHA256 再 base64，随请求带
`timestamp` 与 `sign`；时间戳与服务端相差超过 1 小时会被拒（`19021` 是签名错，`19001` 是
把 access_token 当成了 secret）。

## 3 钉钉

群设置 → 机器人 → 自定义 → 复制 Webhook：

```bash
export DINGTALK_WEBHOOK='https://oapi.dingtalk.com/robot/send?access_token=xxx'
export DINGTALK_SECRET='SECxxx'        # 安全设置选「加签」时才需要
python main.py config set --channels feishu,dingtalk
python main.py dingtalk test
```

PowerShell 用 `$env:DINGTALK_WEBHOOK='...'`；想持久化写进用户环境变量，改完**要重启常驻进程**
才读得到（进程继承的是启动时的环境）。

三个约束决定了它的用法：

- **一轮只发一条**。钉钉限流 20 条/分钟，超了会被静默丢 10 分钟，所以整批条目合并成一条
  markdown，只有超过 3400 字才分段。
- **markdown 为主，feedCard 也能用**。日报是标题分层 + 要点 + 原文链接；`msgtype: feedCard`
  同样能发（`links[].picURL` 给右侧缩略图）。两者都不支持交互元素。
- **地址与密钥只存在环境变量里**。配置里只记变量名，`config.json` 不会把 token 写出去；
  错误信息里的 `access_token` 也会被打码后才进日志。

加签算法是 `HmacSHA256(secret, f"{timestamp}\n{secret}")` → base64 → urlEncode，时间戳为毫秒、
允许 ±1 小时误差，机器时钟要准。若安全设置用「自定义关键词」，消息里必须含那个词
（`intel` 比较合适）。

## 4 Telegram

```bash
export TELEGRAM_BOT_TOKEN='123:ABC'
export TELEGRAM_CHAT_ID='-100123456'
python main.py config set --channels telegram
```

一条事件一条消息，避免长文被 4096 字符截断。零产出时的心跳也会走这条线。

## 5 不带图（已定）

推送只有文字 + 原文链接，**不发图**。三个通道的边界不同，凑不出统一形态：

| 通道 | 图片能力 | 实测 |
|---|---|---|
| 钉钉 markdown / feedCard | `![alt](url)` / `picURL` 都收 | `errcode: 0` |
| 飞书卡片 | 只认 `img_key`，不接受 URL | `11246 / 200570 card contains invalid image keys` |
| 飞书 `lark_md` | `![](url)` 当普通文本 | `code 0`，不渲染 |
| Telegram | `sendPhoto` 可吃 URL | 未接 |

飞书是死结：`img_key` 只能由 `POST /open-apis/im/v1/images` 换取，该接口要 `tenant_access_token`
（无 token 实测 `99991661 Missing access token`），也就是个人版 webhook 机器人**永远发不了图**。

加上采集侧本来就没有图片字段（RSS 解析只读 `title`/`link`/`pubDate`/`description`，
`enclosure`、`media:content`、`content:encoded` 里的 `<img>` 全丢），决定统一不带图：
点开原文就有图，不值得为此破掉「零权限申请」这个前提。完整推演见
[设计方案 §14](../../docs/AI推送智能体-设计方案.md)。

## 6 飞书待办（可选）

只做两件事：把值得动手的那条写成待办、把「前置检查 / 步骤 / 后置验证」写进描述。
**只建不回读**——不回读完成状态，也就不会「没勾就一直催」，那是另一套系统。

```bash
export FEISHU_APP_ID='cli_xxx' FEISHU_APP_SECRET='...'
python main.py config set --channels feishu --feishu-mode app --feishu-receive-id oc_xxx
python main.py config set --feishu-tasks on
```

应用需要 `task:task:write` 权限；`tasklist_guid` / `assignee_open_id` 可选。建过的 URL 记在
`tasks_out` 表里，重跑不会重复建。

## 7 反馈

反馈**只有控制台一个入口**：消息里不带任何按钮，每条末尾只留一行控制台地址。理由很实际——
webhook 机器人收不到卡片回调，按钮点了也没用；而「没用」要选原因，手机上点两下按钮凑不出这个信息。

反馈**按关注项记账**：同一来源在「金融」里被点了没用，不会连累「AI 工程」的权重。
生效权重 = 全局权重 × 该关注项自己的系数，夹在 0.5–2.5 之间。

「没用」必须选一个原因，原因决定扣多少（[`intel/feedback.py`](../intel/feedback.py)）：

| 原因 | 乘数 | 说明 |
|---|---|---|
| 跑题、不相关 `off_topic` | ×0.96 | 主题没对上，来源本身没错 |
| 已经看过、重复 `duplicate` | ×1.00 | 去重问题，只记录不扣 |
| 太浅、没信息量 `shallow` | ×0.92 | 内容质量问题 |
| 标题党、营销稿 `clickbait` | ×0.88 | 标题与正文不符 |
| 来源不可信 `unreliable` | ×0.82 | 最重的一档 |
| 太旧、不是新闻 `stale` | ×0.97 | 时效问题，轻微 |

不选原因时仍是 ×0.90（老行为）。控制台反馈页顶部会按原因汇总近 30 天的分布。

```bash
python main.py feedback                            # 列出最近收录的条目与已给过的反馈
python main.py feedback --topic sec-rev --limit 10 # 只看某个关注项
python main.py feedback --id <item_id> --action up # 有用 / save
python main.py feedback --id <item_id> --action down --reason shallow   # 没用 + 原因
python main.py stats --topic sec-rev               # 该主题每个来源的有效权重拆解
python main.py stats                               # 全局权重、原因分布、今日 token、最近运行
python main.py trace                               # 最近一次各阶段耗时与错误
```

控制台「反馈」页：下拉选关注项 → 每条三颗按钮（有用 / 没用 / 收藏）；点「没用」就地展开
六个原因，选完才记账。没有主题归属的老条目，反馈仍然落到全局。
